# QA Track v0.1.1

> Patch release — multi-impacto em cards do Kanban + filtragem na configuração de Features.

---

## Novidades

### Kanban — Impacto cascata em cards
Um card agora pode declarar impacto em **múltiplos sistemas** e **múltiplas features por sistema**, refletindo cenários reais em que uma mudança afeta vários módulos.

- Novo modelo de dados: tabela N:N `t_card_impact (card_id, system_id, feature_id)`. Os campos `t_card.system_id` e `t_card.feature_id` continuam existindo como **primary pair** (o primeiro par cadastrado) para compatibilidade com leituras legadas.
- A run vinculada ao card recebe o **DISTINCT** dos cenários ativos que casam com qualquer par. Sem duplicação quando o mesmo cenário se aplica a vários pares.

### Propagação ao vivo na Run
Editar os impactos de um card depois da criação **atualiza a run associada em tempo real** e retorna uma mensagem do que mudou.

- `PATCH /api/kanban/card/:id` aceita `pairs[]` e calcula o diff de cenários:
  - cenários novos entram como **Planned** em `t_run_detail`
  - cenários removidos saem do detalhe (independente do `result_status`)
  - se o card ainda não tinha run e os novos pares cobrem cenários, a run é criada nesse momento
  - resposta inclui `runUpdate: { runId, added, removed, created, message }`
- A UI mostra um **toast** no topo do board com a mensagem, e.g.: *"Run #42 atualizada: +3 cenário(s), -1 cenário(s)"*.

### UI — Editor de impactos
Modal de criar/editar card foi reformulado para um editor de linhas:

- Cada linha é um **sistema impactado** com **multi-select de features** dele (size=5, contador de selecionadas).
- Sistemas já usados em outras linhas somem do dropdown da próxima linha (evita duplicar).
- Botão **+ Adicionar outro sistema impactado** para incluir N linhas.
- Cards no board mostram `N sistemas · M pares` quando há mais de um sistema.

### Config — Filtro de Features por sistema
A aba **Features** da página de Configuração ganhou filtros pra não jogar a lista inteira na tela quando há volume:

- Dropdown **Todos os sistemas** filtra a lista pelo sistema escolhido.
- Campo de busca por **ID ou título** (case-insensitive).
- Contador `X/Y` quando há filtro ativo.
- Botão **Limpar** quando algum filtro está em uso.
- Mensagem dedicada quando o filtro não retorna nada (vs lista vazia).

## Compatibilidade

- **Backward-compatible no POST/PATCH**: o shape antigo `{ system_id, feature_id }` continua funcionando (interpretado como `pairs: [{...}]`).
- **Backfill automático**: cards existentes têm seu par `(system_id, feature_id)` inserido em `t_card_impact` na primeira aplicação do schema.
- **Mover card para `Finalizado`** continua exigindo todos os cenários da run como `Passed` — incluindo os incorporados via cascata.

## Endpoints alterados

| Verbo | Rota | Mudança |
|-------|------|---------|
| POST | `/api/kanban/card` | aceita `pairs[]` ou `impacts: [{system_id, feature_ids[]}]` (além de legado) |
| PATCH | `/api/kanban/card/:id` | aceita `pairs[]`; resposta inclui `runUpdate` se cenários mudaram |
| GET | `/api/kanban/card`, `/api/kanban/card/:id` | resposta inclui `pairs[]` e `impacts[]` agrupados por sistema |

## Schema

```sql
CREATE TABLE IF NOT EXISTS t_card_impact (
    card_id    INTEGER NOT NULL REFERENCES t_card(id) ON DELETE CASCADE,
    system_id  INTEGER NOT NULL REFERENCES t_system(id),
    feature_id INTEGER NOT NULL REFERENCES t_feature(id),
    PRIMARY KEY (card_id, system_id, feature_id)
);

-- Backfill idempotente
INSERT INTO t_card_impact (card_id, system_id, feature_id)
SELECT id, system_id, feature_id FROM t_card
WHERE system_id IS NOT NULL AND feature_id IS NOT NULL
ON CONFLICT DO NOTHING;
```
